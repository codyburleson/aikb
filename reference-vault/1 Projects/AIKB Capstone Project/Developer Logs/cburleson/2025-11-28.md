

# Pull Request Review

I think there may be a problem with the latest pull request. In the @aikb-spec.md , which is the formal specifications, it says that we should be following YAML 1.2 at https://yaml.org/spec/1.2/ . However, we have JSON like values in in the notes that are created from templates because the templates have values like `{date}` in the metadata (placeholders). If you look at @AIKB Capstone Project.md , you will see that when I create that file using the Project template, it puts values like `{date}` in the frontmatter because that is in the template. However, my tool, Obsidian, expects these values either to be populated with the type or empty. So, I am not sure these are legal values in YAML. Is there a way that we can get the smae functionality without having the placeholder variables in the templates like `{date}`? We need to find out why these are necessary and think of a better solution. It would be better, for example, to just use something similar to what Obsidian does in `reference-vault/.obsidian/types.json`. If we need to know the types of the fields, we can have a JSON schema as some separate file that defines the types and then we can use that to populate the frontmatter?

## Proposed Solution

### Problem Analysis

The `{date}` and `{title}` placeholders in templates create three core issues:

1. **YAML 1.2 Compliance**: The spec requires YAML 1.2 compliance (line 272 of `aikb-spec.md`), but `{date}` is not a valid YAML value - it's a placeholder string that's neither a proper date nor quoted as a string literal.

2. **Obsidian Compatibility**: Obsidian expects these fields to be either properly typed values or empty. The `{date}` placeholders break Obsidian's type system defined in `types.json`.

3. **Template vs Instance Confusion**: The current templates mix two concerns:
   - **Template definition** (what fields should exist)
   - **Instance creation** (placeholder values for new documents)

### Recommended Approach: Separate Concerns

Similar to how Obsidian handles it with `types.json`, we should separate structure from type definitions:

#### 1. Templates with Empty Values

Templates should have **empty values** for fields that will be populated:

```yaml
---
name:
type: "[[Project]]"
tags:
  - type/Project
created:
updated:
startDate:
endDate:
---
```

#### 2. Type Definitions via JSON Schema

Type definitions should live in JSON Schema files (`.aikb/schemas/Project.json`):

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "type": { "type": "string", "const": "[[Project]]" },
    "tags": { "type": "array", "items": { "type": "string" } },
    "created": { "type": "string", "format": "date-time" },
    "updated": { "type": "string", "format": "date-time" },
    "startDate": { "type": "string", "format": "date" },
    "endDate": { "type": "string", "format": "date" }
  },
  "required": ["name", "type"]
}
```

#### 3. Agent Logic

Agents would:
- Read the template file
- Read the corresponding JSON schema
- Populate empty fields with appropriate values (current date, user-provided title, etc.)
- Validate against the schema before creating instances

### Benefits

1. ✅ **YAML 1.2 Compliant**: Empty values are valid YAML
2. ✅ **Obsidian Compatible**: Works with `types.json` type system
3. ✅ **Separation of Concerns**: Template structure separate from type definitions
4. ✅ **Agent-Friendly**: JSON Schema provides clear validation rules
5. ✅ **Human-Friendly**: Templates are clean and understandable
6. ✅ **No ambiguity**: Clear what's structure vs what's placeholder

### Implementation Tasks

1. Update all core templates to use empty values instead of placeholders
2. Create JSON schemas for each core entity type in `.aikb/schemas/`
3. Update the AIKB specification to clarify this approach
4. Update agent code (`src/agent.py` and `src/tools/markdown_ops.py`) to:
   - Read JSON schemas to understand field types
   - Populate empty fields appropriately during instance creation
   - Validate instances against schemas
5. Ensure backward compatibility or migration path for existing documents

## JSON vs YAML Processing Issue - 11:00 AM

### Problem Identified

Found improper mixing of JSON and YAML processing in `src/tools/markdown_ops.py`. Since frontmatter metadata is YAML, we should not be using JSON for these operations.

### Specific Issues Found

#### 1. `update_frontmatter` Function (Lines 262-281)

**Current Implementation:**
```python
def update_frontmatter(path: str, updates_json: str) -> dict:
    """
    Updates the frontmatter metadata of an existing markdown file.
    updates_json: JSON string containing the metadata updates.
    """
    updates = json.loads(updates_json)  # ❌ Using JSON
    post = frontmatter.load(full_path)
    post.metadata.update(updates)
```

**Problems:**
- Parameter is named `updates_json` suggesting JSON input
- Uses `json.loads()` to parse the updates
- Forces the agent to send YAML metadata as JSON string
- Creates unnecessary serialization/deserialization step

**Proposed Solution:**
```python
def update_frontmatter(path: str, updates_yaml: str) -> dict:
    """
    Updates the frontmatter metadata of an existing markdown file.
    updates_yaml: YAML string containing the metadata updates.
    """
    import yaml
    updates = yaml.safe_load(updates_yaml)  # ✅ Using YAML
    post = frontmatter.load(full_path)
    post.metadata.update(updates)
```

#### 2. `_sanitize_metadata` Helper (Lines 73-90)

**Current Implementation:**
```python
# Helper to fix JSON serialization issues with dates
def _sanitize_metadata(metadata: dict) -> dict:
    """
    Converts non-JSON-serializable objects (like dates) to strings.
    """
```

**Problems:**
- Comment and docstring reference "JSON serialization"
- This function is used to prepare metadata for return values
- Misleading name and documentation

**Proposed Solution:**
Either:
1. Rename to `_sanitize_for_return` and update docs to clarify it's for return values (not JSON-specific)
2. Consider if we even need this - the `frontmatter` library handles YAML serialization properly

#### 3. JSON Schema Files (Correct Usage)

**Current Implementation:**
