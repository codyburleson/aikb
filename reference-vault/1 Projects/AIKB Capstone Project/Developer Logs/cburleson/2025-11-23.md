  ## Implementation

  ### Tools Developed
I have implemented the following tools in `src/tools/markdown_ops.py`:
- `read_markdown(path)`: Reads frontmatter and content.
- `create_markdown(filename, content, folder, metadata_json)`: Creates a new note with metadata.
- `update_frontmatter(path, updates_json)`: Updates metadata.
- `update_content(path, new_content)`: Updates the file content while preserving frontmatter.

### Libraries Used
- `python-frontmatter`: For metadata management.

### Integration
The tools are integrated into `src/agent.py` and registered with the `root_agent`.

### Verification
A verification script `verify_markdown_tools.py` was created and successfully verified all operations.
Manual testing with the agent confirmed that it can create notes using natural language commands.

### Challenges & Solutions
- **Tool Signatures**: The Agent API had issues with `dict` type arguments. I converted complex arguments to JSON strings (`str`) to ensure compatibility.
- **AST Complexity**: Initially, I implemented AST-based tools using `marko`. However, this proved complex and inefficient (token bloat). I refactored to use a simpler `update_content` approach, relying on the LLM's native ability to rewrite Markdown.

## Lessons Learned

The operations are working as expected, but they seem to be a bit slow.

### AST vs. Raw Markdown
We discovered that explicit AST parsing (using `marko` to convert Markdown to JSON) might be unnecessary and even counterproductive for an LLM-based agent.

1.  **Token Bloat**: Converting Markdown to a JSON AST significantly increases the token count (often 10x or more), which slows down inference, increases latency, and raises costs.
2.  **LLM Capability**: Modern LLMs are "native speakers" of Markdown. They understand structure (headers, lists, etc.) intuitively without needing a structured JSON tree.
3.  **Complexity**: Maintaining AST reconstruction logic is complex and prone to bugs (as seen with the `marko` library issues), whereas asking the LLM to "rewrite the header" is robust and simple.

**Conclusion**: For future iterations, we should consider deprecating the AST tools in favor of simple text-based manipulation or full-file rewrites by the LLM, unless deterministic, code-enforced rules are strictly required.
